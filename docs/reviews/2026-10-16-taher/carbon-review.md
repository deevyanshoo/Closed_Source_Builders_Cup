## Release blockers

1. **P1 — The displayed material-plus-freight total has an overlapping boundary and an unsupported global geography.** `procurement-engine/config/carbon_factors_v1.json:5,64-71` explicitly says the DESNZ material factor includes transportation to point of sale and PET forming, yet `procurement-engine/src/procure/carbon/calculator.py:109-116` adds the entire entered leg and marks the sum complete. `apps/web/src/demo-carbon.tsx:32,79-85` presents it as a supplier total. The official 2026 methodology, section 12.2, says primary material factors include transport to point of sale; section 12.19 says material factors include forming. GOV.UK says these factors are intended for UK activities and other uses are at the user's risk. A reproducible 8,000 kg PET example with one 1,000 km container leg reports material 30,892.66008 + freight 128.96 = **31,021.62008 kg CO2e**. Some or all of the 128.96 leg can overlap the embedded transport; the exact overlap is unknowable from this registry. The factor also includes forming that a resin purchase has not yet undergone. A global Singapore–India scenario uses this UK average without a geography suitability flag. Keep material and entered freight as separate, explicitly bounded scenarios until origin, sale point and nonoverlapping segment are established; do not show their sum as a complete footprint. PET resin needs a resin-specific factor or a prominently unavailable/upper-bound state.

2. **P1 — Carbon export is lost on a persisted hosted session.** `procurement-engine/src/procure/demo/carbon_api.py:53-54` sets `value.carbon_estimate` dynamically, while `procurement-engine/src/procure/demo/sessions.py:29-42,98-105,233-236,315-352` omits it from dataclass, serialized state and restore. The middleware saves the session (`procurement-engine/src/procure/demo/app.py:128-136`), but a new process restores it without the estimate; `/api/demo/export` then returns `carbon: null` via `carbon_export` (`carbon_api.py:13-19`, `app.py:2107-2125`). Reproduced with `MemorySessionPersistence`: set `carbon_estimate`, save, instantiate a fresh `SessionStore`, restore the same ID: `before {...}; after None`. The existing export test uses an ephemeral in-process store, so it misses this hosted behavior. Make the result a bounded validated persisted field (and company workspace member if intended), or explicitly make export recompute from persisted, versioned inputs; test cold restore and switch/revisit.

3. **P2 — A partial result has a numeric `total_kg_co2e`.** `procurement-engine/src/procure/carbon/calculator.py:103-116` sums all available parts even if transport is incomplete, because `parts` includes the material and `total` only checks that material is present. With 8 t PET and an unknown 1,000 km mode: `transport.status=incomplete`, `complete=False`, but `total_kg_co2e=30892.66008`. The current UI checks `complete`, but JSON export and downstream clients can interpret `total_kg_co2e` as a whole-scenario total. Make total null unless all required components are estimated, or call it an explicit partial subtotal.

4. **P2 — Carbon stays actionable after buyer inputs are edited.** `apps/web/src/demo-page.tsx:29-30,657,660-661` marks the existing comparison dirty on an input edit but still renders `PlanResults` and `CarbonPanel`; `demo-carbon.tsx:69-83` can submit its old `plan_id`. The API validates against the still-active server plan (`carbon_api.py:44-50`), which is unchanged by local edits. Reproduction: compare, edit needed quantity, click Estimate emissions before rerunning comparison; it succeeds for the previous quantity and can appear alongside current edited controls. Gate display/submit on the same dirty/current-plan conditions as other plan actions. Stale-response plan-ID gating handles a newly created plan, but does not resolve the local dirty interval.
