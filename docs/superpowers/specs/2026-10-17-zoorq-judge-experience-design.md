# ZOORQ judge experience design — 17 October 2026

## Purpose and boundary

This is a design for the next increment, not evidence that it exists. It starts from clean `feature/zoorq-taher-integration` at `40fcc553aead39a3f3951fc741ba48c052a901d4`. The outcome is a judge-readable, source-grounded decision journey in the existing synthetic workspace: open a prepared company, inspect an observed signal, preview a matched disruption, compare the same baseline and recovery, and optionally review an unsent RFQ. Video recording, supplier outreach, final submission and claims of customer savings are outside this increment. Arbitrary-company onboarding remains an approved-feedback item deferred to a separate milestone; this increment keeps the ten existing profiles discoverable.

The current r74 all-company and targeted receipts are historical acceptance for their own revision. Every new interaction needs new local, native, browser and exact hosted evidence. The one top-of-workspace disclosure remains the routine synthetic/proxy notice; material missing data, planned status and consent/action rules are still shown at the point of use.

## Decision and research flow

One server-owned resolver receives the current `operator_snapshot`, user utterance, channel and freshness intent. It returns a primary kind of `internal_answer`, `read_only_preview`, `needs_input`, `research_proposal`, or `unavailable`, with current company/context/plan identifiers and evidence references. A mixed local-and-fresh question may return an `internal_answer` plus a separately consentable `follow_up_research` proposal for the unresolved public-news part; the local answer must not wait for external search. Evaluation order is: current workspace inventory, reviewed quotes, active plan, shipment and carbon assessment; cached current-company News and Global Watch; completed relevant approved research history; then an exact missing-input request. External public research is offered only for an actual evidence gap or an explicit fresh-search request, and runs only after its exact public query/destination is displayed or spoken and freshly approved. A stale cached observation is identified as stale; it is not silently passed off as current. An explicit fresh-search request cannot be satisfied merely by old history. The resolver does not send private workspace data to the public search adapter.

This is a shared control path, not prompt wording. Today `demo/app.py:execute_operator_turn` and `demo/operator.py:run_turn` try `prepare_research` before integration and broad inventory; native `prepare_research` in `demo/app.py:workspace_tools` re-enters the typed turn. The new resolver runs ahead of all three entry points and uses one policy. Existing session/company/material/plan and quote-version ownership, context version, operator generation, expiry, pending-proposal marker, research budget/claim, consent, cancellation and idempotency remain authoritative. On interruption, company switch, context change or stale provider completion, no old answer, consent gate or scenario result is surfaced. Read and preview operations cannot apply a recovery, prepare a send, or send an RFQ. Apply and draft remain separate reviewed actions.

The what-if preview accepts a selected current shipment/offer and an explicit whole-day delay. “Supplier 7-day delay” needs a selected owned supplier/shipment or asks which one; it never picks a different company. “Suez 14-day disruption” requires a current material and route that actually match a Suez lane plus the user's explicit 14-day planning assumption. The same route-matched flow must handle a generic port or shipping disruption for any of the ten companies: require an explicit location or owned route segment, duration and material, resolve affected current shipments/offer bindings within that company, and preview only compatible routes. Text and voice both ask for missing inputs, state unsupported or unmatched routes clearly, and never fabricate a port, shipment or delay. A public blockage advisory alone establishes no affected current shipment, delay, probability or financial loss. The existing `recovery.compare` and current dispatch/plan bindings produce the preview; an infeasible result remains infeasible. Text and Gemini Live use the same response facts, with the model explaining rather than calculating. Speech must survive interruption, switching companies and repeated tool events without a duplicate action.

## Route simulation

The Supply view gains an optional Google Maps JavaScript visualization of a *simulated* itinerary: declared vendor area → road truck → origin port → sea ship → destination port → road truck → chosen buyer city/location. The selected material, route ID, supplier/offer ID and buyer location bind the view; users choose among a company's listed buyer locations. A versioned `route_display_v1.json` records each supported display lane's IDs, approximate waypoints, source/provenance, precision, mode, geometry and explicit unsupported segments. It may draw from the eight approximate, unverified ports in `procurement-engine/config/locations_v1.json`, but does not promote them to verified coordinates or invent an exact vendor/facility address. Every company gets a useful text route overview; an incomplete lane shows only supported segments and a clear missing-detail label.

Play/pause, speed, timeline scrub, disruption marker and baseline/recovery comparison drive a deterministic local animation. The timeline never changes authoritative arrivals, prices, carbon or plan status. Map distance is visual only: it is not silently entered into carbon or planning. Land routing may be used only for suitable, verified land endpoints and only if its API is separately justified and enabled; the planned first version uses curated display geometry and Maps JavaScript only. Google's Routes modes list land travel modes, with no sea/vessel mode, so the marine path is curated simulation and never live vessel tracking. Reduced-motion users get a static map and usable timeline/list; mobile and Maps-unavailable states keep a complete list fallback. Google map attribution remains visible. [Routes modes](https://developers.google.com/maps/documentation/routes/reference/rest/v2/RouteTravelMode), [Maps JavaScript API](https://developers.google.com/maps/documentation/javascript/overview).

Maps JavaScript API is enabled in `closed-source-builder-261007`. The existing GCP Console browser key named `ZOORQ browser maps` is restricted to Maps JavaScript API and the two existing demo origins. Its value must never be read, printed, copied or committed. The future `zoorq` origin is not yet in its website restrictions; the coordinator must add the exact final origin and verify the resulting referrer/API restrictions before using Maps there. Inspect current quota/cost under the existing trial credits before use. No enable-all, new subscription, billing upgrade or out-of-pocket commitment. The map's complete list fallback remains available until the new-origin check passes. [Google key restrictions](https://developers.google.com/maps/api-security-best-practices), [Maps setup](https://developers.google.com/maps/documentation/javascript/get-api-key).

## Evidence, impact and AI receipt

The Suez 2021 replay is a dated historical demonstration built from curated Maersk advisories. Each advisory stores source URL, its specific publication/update section and time, exact available excerpt or fact, retrieval time and display license/attribution. The [Maersk Suez advisory](https://www.maersk.com/news/articles/2021/03/24/vessel-blockage-in-the-suez-canal) is a living page: its March 24 URL currently contains later updates through April 20. Pin each fact to its dated update section, not the URL date or current page heading. Replay time gates evidence: a frame cannot use an advisory published later than that frame. The actual blockage, published carrier updates and any reported reaction dates are distinct from a simulated company alert or chosen delay. No invented three-week early warning. The implementer must archive and verify the specific dated updates used.

The impact card uses the *same owned baseline and scenario* for days of gap, planned spend exposed, additional recovery cost and compatible carbon. Planned-spend exposure comes from deduplicated affected order quantities and compatible reviewed quote prices with Decimal arithmetic, explicit unit/currency/as-of and unavailable states. It is not realized loss, and recovery `cost_delta` is additional scenario cost, not loss or customer savings. Carbon comes only from the authoritative compatible assessment; unsupported whole-scenario totals stay unavailable. The card includes baseline/scenario IDs and source links so the displayed differences can be reproduced.

A visible, truthful “Built with Gemini, Vertex AI and Cloud Run” panel lists actual roles: Gemini interpretation/translation or operator explanation when a real provider call succeeds; Vertex AI as its model-serving path; Cloud Run as the hosted app/service. The Hindi case needs one bounded real Gemini call through Vertex AI on a sourced public excerpt, with a source ID and bounded prompt. Sanitize and persist a server-owned receipt containing the actual model ID/version, provider call ID when returned, input source ID, call timestamp, translation/summary output, status and evidence references; keep raw provider payloads, credentials and private workspace data out of Git and UI receipts. The panel shows dynamic per-run counts, for example “Gemini interpreted N real input articles and flagged M for review,” only from successful retained receipts with distinct input IDs and actual model-reviewed flags. Failed/skipped calls and deterministic ranking cannot contribute. Deterministic route drawing, ranking, calculation and planning are labelled as such, never as AI. No fixed “40 articles” claim.

The candidate multilingual source is the [official Hindi PIB release dated 30 May 2026](https://www.pib.gov.in/PressReleasePage.aspx?PRID=2267065&lang=2&reg=48), with the [Gazette notification No. 19/2026-Customs](https://static.pib.gov.in/WriteReadData/specificdocs/documents/2026/may/doc2026530879601.pdf) as corroboration. The Gazette identifies cotton under heading 5201 imported into India and exempts the stated customs duty and Agriculture Infrastructure and Development Cess from 1 June through 31 October 2026, inclusive. Preserve the Hindi original, issuer, publication/retrieval dates, notification scope and real Gemini English translation/summary receipt. Link an Indian cotton material/route only through an owned profile and evidenced regional exposure. The LoomWorks Delta Cotton and Meridian India API supplier fixtures are synthetic records, not proof of supplier stock, price or direct exposure; neither source establishes a Bangladesh import-duty change. StoneBridge's South Africa buyer is another real profile context, not a Brazil supplier. A Portuguese/Brazil extension is optional only after real source and profile work. English speech may explain the Hindi source; Hindi voice is a release claim only after native and physical-microphone testing. Translation uncertainty and original-source access remain visible.

## Entrance, sharing and release origin

The root route opens a populated flagship workspace within a measured first ten seconds on the tested network/device, with its selected synthetic baseline, one top disclosure, persistent company navigation and a direct route to the signal/what-if journey. Returning sessions keep their current company/state; first-run seeding is idempotent, confined to synthetic fixture plans and performs no approved business action. No signup or upload is required for the judge journey. All ten companies remain available through Company Explorer; its lightweight discovery is lower priority than the flagship path and uses only current profiles, not invented relationships. Public research from Explorer uses the same consent gate. Full arbitrary-company onboarding is separate.

`apps/web/index.html` gains canonical, OpenGraph, Twitter and `noscript` metadata and a real share-card asset. The final canonical URL is an absolute final `zoorq` URL, never a placeholder, session URL or old service alias. Inspect raw deployed HTML and image without JavaScript and verify MIME, dimensions, size and no private URL. Cloud Run cannot rename the existing service: the coordinator plans a clean new `zoorq` service from a reviewed immutable image in the existing project/region, matching reviewed service account, persistence and resource/concurrency/timeout/max-instance limits. The old service/link stays working. The new service's public invocation scope is reviewed separately; a custom domain is optional only if already owned and authorized. New-origin session cookie, CSRF/origin, research consent, canonical and Maps referrers receive explicit tests. [Cloud Run traffic and rollback](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration), [public invocation](https://docs.cloud.google.com/run/docs/authenticating/public).

## Acceptance and open gates

Release requires scenario arithmetic/provenance regressions, resolver parity in typed and native Live voice, interruption/company-switch/stale-result checks, generic port/shipping missing-input and unsupported-route checks across all ten companies, one successful bounded Hindi Gemini/Vertex receipt or an explicit unavailable state, all-ten route-overview coverage, mobile/reduced-motion/list fallback, accessible keyboard controls, raw static metadata validation, measured first-ten-second entrance, Lighthouse/performance review and physical microphone/manual QA. Use exact final revision receipts; r74 evidence does not count as new-feature acceptance. Interview plans may be drafted, but a real user quote requires an actual interview and consent to quote; no outreach or fabricated quote is authorized now. Video recording is excluded.

Storage is a **build preflight check**, not a current blocker: free space recovered from the earlier 136–159 MiB; the coordinator measured about 4 GiB, and a 17 October check in this checkout measured 3.1 GiB available. Before any install/build/package, remeasure free space against peak need and stop only if inadequate. No cleanup is authorized in this planning pass. Other conditional gates are a usable Hindi source and successful bounded model receipt, dated Maersk replay evidence, route geometry provenance, final `zoorq` URL, Maps quota and the new-origin key restriction. Missing evidence produces an explicit unavailable state or defers that showcase claim; it does not invite invented facts.
